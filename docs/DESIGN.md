# AgentTerm design

How AgentTerm is built and why. For what it should do, see [SPEC.md](SPEC.md).

## Overview

```
 iPhone app ──┐                      ┌── PTY ── claude
              │  WebSocket           │
              ├──(Tailscale)──┐      ├── PTY ── codex
              │               ▼      │
 macOS app ───┴─(loopback)─ agenttermd ┴── PTY ── zsh
```

One process, `agenttermd`, owns every terminal session. The macOS app and the
iPhone app are both clients of it and speak the same protocol. The macOS app
has no private path to the terminals, so everything it can do is something the
iPhone can do too, and the protocol is exercised every time the Mac app is used.

## Modules

| Module | Platforms | Role |
|---|---|---|
| `AgentTermProtocol` | macOS, iOS | Message types, binary frame, pairing URL. No dependencies. |
| `AgentTermHost` | macOS | `PTYProcess`, `SizeArbiter`, `HostServer`, agent detection, Tailscale lookup, git diff, daemon launcher. |
| `agenttermd` | macOS | Command line entry point around `HostServer`. |
| `AgentTermClient` | macOS, iOS | `AgentTermConnection`, a WebSocket client built on Network.framework. |
| `AgentTermTerminal` | macOS, iOS | `TerminalController`: a SwiftTerm view bound to one session, plus shared colors. |
| `AgentTermMac` | macOS | SwiftUI app. |
| `iOS/AgentTerm` | iOS | SwiftUI app. Not part of the package. |

The package is plain SwiftPM. The iPhone app needs an app bundle, so it has an
Xcode project, generated by XcodeGen from `iOS/project.yml` and not checked
in. It depends on the package's `AgentTermProtocol`, `AgentTermClient` and
`AgentTermTerminal` products.

The client uses Network.framework rather than `URLSession` because the host
speaks plain `ws://`. App Transport Security would refuse that for
`URLSession` on iOS, and an exception for arbitrary loads is broader than
needed. The connection is made to a URL endpoint: with a host and port
endpoint the WebSocket handshake is aborted.

## Pseudo terminals

`PTYProcess` starts the child through `agentterm_spawn_pty`, a small C function
(target `CAgentTermPTY`) that forks, calls `setsid()` and `ioctl(TIOCSCTTY)` on
the slave side, sets the window size, and execs.

- The pseudo terminal has to be the child's *controlling* terminal, or the
  child gets no terminal signals: no SIGWINCH on resize, so a full screen
  program never redraws for a new size. `posix_spawn` cannot do this, because
  it cannot run an ioctl in the child, and opening the slave from a spawn file
  action does not make it the controlling terminal. An earlier version did
  exactly that and seemed to work, because bash claims the terminal itself at
  start-up. zsh does not, so everything started through a zsh login shell,
  which is every agent, ran without one.
- Between `fork()` and `execve()` the child only calls async-signal-safe
  functions, which is what makes `fork()` acceptable in a threaded process.
- The child closes every descriptor but the terminal, so the daemon's sockets
  and other terminals are not passed on, and resets signal handling.
- A failed exec is reported back through a close-on-exec pipe.
- Output is read by a dispatch source on the host queue. Writes run on a
  separate queue because they block when the program is not reading, and
  output must keep flowing meanwhile.
- When the child exits, pending output is drained before the exit is reported.

Programs are started through the user's login shell (`$SHELL -l -i -c
<command>`), so they get the same `PATH` and environment as in a regular
terminal. The environment sets `TERM=xterm-256color`, `COLORTERM=truecolor`
and a UTF-8 locale when none is set.

## Terminal size with several clients

A PTY has one size, but a Mac window and an iPhone screen differ. `SizeArbiter`
implements "the client being used wins":

- Every attached client reports the grid that fits its view, and reports
  again when that changes (`resize`).
- The driver is the client that most recently took control (`takeControl`) or
  typed. The PTY takes the driver's size.
- Attaching and resizing never make a client the driver, unless it is the only
  one attached. The Mac app attaches to every session to show it; if that took
  the size, a session opened on a phone would jump to the Mac's size a moment
  later and the phone would only see a corner of it.
- A client's reported size is kept while another client drives, so typing
  there later switches to its current size at once.
- When the driver detaches, a driver that used the session (took control or
  typed) leaves its size: nobody drives until a client uses the session
  again, and the size stays (`SizeArbiter`, SIZE-8). The program's
  questions to its terminal are answered meanwhile by the most recently
  active client (`answerer`). A driver that only watched, being the only one
  there, hands over to the most recently active remaining client. With no
  client left the size stays as it is.
- The iPhone takes control of the session open on it whenever its replay
  ends, so coming back after it was away takes the phone's size at once. The
  Mac app takes control when a key is typed or the terminal is clicked.
- After every change the host sends `resized` to each attached client with a
  `driver` flag. A client that is not the driver shows the driver's grid
  rather than its own, so the content lines up.

tmux's rule, the smallest attached client, was rejected: a phone left
connected would keep the Mac window small.

Size reports are debounced by 120 ms, because layout changes arrive in bursts
(a window being dragged, the iOS keyboard sliding in) and each report makes
the program redraw.

`TerminalController` keeps two sizes: the natural size that fits
its view and the foreign size imposed by another driver. A layout change while
another device drives updates the natural size without taking control.

The iPhone attaches only to the session on screen, takes control of it when
it opens, and detaches when leaving it, so the Mac gets its size back as soon
as the phone stops looking. The Mac takes control only when the user types or
asks for it.

While a session has a foreign size, every client's emulator takes that grid,
so all of them draw exactly what the driver sees. The terminal view is then
made exactly as large as the grid (SwiftTerm's `getOptimalFrameSize()`), and
the container decides how to show it:

- **Mac**, where the foreign grid is usually a phone's and small: centered,
  with a frame and a dimmed surround.
- **iPhone**, where it is usually a Mac's and large: scaled down with a view
  transform until the whole grid fits, against the top.

Because the view no longer has the container's size, what SwiftTerm reports
as its size is the foreign grid. The grid that would fit the container, which
is what the client asks for when the user comes back to it, is worked out by
`TerminalController.containerResized` from the cell size. Once the client
drives again the view fills the container and SwiftTerm's own figure is used.

Keeping the Mac's own, larger grid and letting the narrower output flow into
it was tried and dropped: it reads well for programs that draw relative to
the cursor, but the picture on the Mac is then not the picture on the phone.

### Writing a screen out off the sessions' queue

Each session's `ScreenMirror` is used only on a queue of its own
(`mirrorQueue`): its output is fed there, it is resized there, and a client
that attaches gets the screen written out there, 82 ms for 10,000 lines,
while the queue every session's output and every request go through goes
on (PERF-7). The client is sent `attached` at once; what the session writes
until the screen is ready is kept for it (`awaitingScreen`) and sent after
the screen, so it counts on from the end of it. A newer attach of the same
client drops a screen still on its way.

### Earlier lines a page at a time

`attach` takes `history`: how many lines above the screen to write out,
the nearest ones (`ScreenMirror.snapshot(linesAbove:)`); nil for all.
`replaying` says, in `above`, how many the host keeps. The iPhone attaches
with 500 (`TerminalController.historyAsked`); when the view is scrolled to
its top by a finger (watched on `contentOffset`, since the emulator does not
say it scrolled while a finger moves it), and the host keeps more, it
attaches again with 1,000 more. That replay is drawn over the same
terminal, not a new one, and says so in a strip rather than over the
screen; it does not take the session's size again. Once drawn, a swipe
still coasting is stopped and the row that was at the top is put back by
number, again after the emulator's next frames, which follow its output to
the bottom, until it stays (HIST-6). A reconnect asks with `have` and the
same `history`, and gets only what came since.

### The size a session starts with

A session is created with the grid that fits the place its terminal will be
shown in, worked out by `TerminalMetrics` from that place's size and the
font before any terminal view exists. With a guessed size the shell draws
its first prompt for the wrong width. zsh then leaves a stray "%" on screen:
it prints that mark and pads the line to the width it believes in, and the
padding wraps where the real width is smaller.

That place is the terminal's pane less the room kept around the text
(`TerminalInsets`: 14 points at the sides, 10 above and 8 below on the Mac;
10 at the sides, 8 on its side, and 6 above and below on the iPhone). On the
Mac the launch screen, where a first session is started from, has no strip
of tabs yet, so the strip's height, as last shown, is taken off too (SIZE-7).

The same mark can still show after the width changes later (rotating the
phone, changing the text size, another device taking over), because the
padded line is already on screen and gets wrapped again.

### Input that is not typing

Every attached emulator answers the program's queries (cursor position,
device attributes, colors), and reports focus changes and pointer movement.
These arrive the same way keystrokes do. `TerminalReply` recognizes them, and
the host:

- does not count them as activity, so they never make a client the driver.
  Before this, Claude Code's start-up queries were answered by the Mac's
  emulator, the host took that for typing on the Mac, and a session opened on
  a phone jumped to the Mac's size;
- passes on only the driver's, so the program gets one answer, from the
  emulator whose grid matches the PTY.

## Protocol

WebSocket over TCP, default port 7717.

**Text frames** carry JSON messages, encoded with Swift's synthesized `Codable`
for enums (`{"attach":{"session":1,"size":{"cols":48,"rows":30}}}`).

Host to client: `welcome`, `sessions`, `agents`, `folders`, `attached`,
`resized`, `exited`, `error`, `diff`, `diffFile`, `history`, `directory`,
`commitMessage`, `sshHosts`, `failures`, and for pairing `paired`,
`pairingCode`, `devices`. The session list, the folder list and the host's settings
(`tabLayout`, `keepAwake`, `keepAwakeOptions`, `commitWriter`) are pushed to
every client when they change.

The protocol version is 8 since 0.7.0, which added `agentShellsFaults`
and gave `agentShellResult`'s list of shells the asking agent's own (see
"Shells an agent opens"). It was 7 from 0.6.0, which added `failures` and
`dismissFailure` (see "A part that stopped"), and 6 from 0.4.0, which
added the messages for push and pull, commit messages, keep awake options
and SSH hosts.

The folder list is host state, saved in `folders.json`, so the Mac and the
iPhone show the same projects and the phone can start an agent in any of them.

**Binary frames** carry terminal bytes: one byte kind (0 output, 1 input), the
session id as 4 bytes big endian, then the raw bytes. Input from a client that
is not attached to the session is dropped.

## Attaching to a running session

The host keeps each session's screen: a terminal emulator of its own that
nobody looks at (`ScreenMirror`, SwiftTerm without a view) is fed all the
session writes and follows its size. A client that attaches is sent that
screen written out again as terminal output: the lines above the screen
(10,000 of them at most), the screen, the other screen when a full screen
program is on it, then the margins, the cursor and the modes the program
set (how keys, the mouse and pastes are reported, whether the cursor
shows). To the client it is output like any other, so nothing in the
protocol changed for it. It goes out in pieces of 256 KB, since one message
may not be larger than 4 MB.

Until 0.5.0 the client was sent the last 4 MB of the session's raw output
instead. A full screen program then only looked right once it drew again,
and what had been drawn for another width, before a phone took the session
over, read badly further up. The screen written out again is right for the
size the session has now, and is usually much smaller.

Three things about it are deliberate:

- It holds no question to the terminal (which terminal are you, where is
  the cursor), so a client has nothing to answer a second time. Clients
  still treat it as a replay and send nothing on until `replayed`.
- The emulator's own colors are left out. A client has its own.
- A program's output arrives in pieces cut anywhere, also inside an escape
  sequence or a character. A client given the screen at such a moment would
  get the end of something whose beginning it never saw. So the host also
  follows the output byte by byte (`OutputTracker`) and ends what it sends
  with the beginning of whatever is unfinished. The same tracker remembers
  the few settings SwiftTerm keeps to itself: how the mouse is reported,
  whether lines wrap, the cursor's shape and the colors text was being
  written in.

Not carried over: images, links, tab stops, character sets, origin mode
and the palette a program changed.

A phone that lost its connection attaches again within seconds, with its
terminal still holding all it was sent. Sending the screen again costs
time and cellular data at each change of network, and would throw away
what the terminal had scrolled back to. So the host also keeps the last
1 MB of each session's raw output and says where in the session's output
what it sends ends up (`replaying(session, from)`, the place of the first
byte, counted so that the end of a screen is where the session is now).
The terminal counts on from there (`TerminalController.position`), and
attaching again names that place (`have`): the host then sends only the
raw output that came since. When it no longer keeps that far back, or the
place is not one of this session's, it sends the screen and says so with
another `from`, and the client starts a new terminal for it. The Mac app
does not use this: it loses its connection only when the host itself
stops, and its sessions with it.

The replay was drawn for the session's grid, so the emulator takes that
grid before the first replayed byte (`TerminalController.beginReplay(size:)`),
and keeps it until its view has been laid out and the grid that fits is
known. Before 0.4.0 the emulator replayed at the size it happened to be
created with and then went to 80 × 24: lines wrapped in the wrong places,
and a program that redraws in place, an agent above all, showed a broken
screen. Nothing made it draw again, because the Mac attaches at the
session's own size, so the size never changed. It showed whenever the app
was opened with an agent already running, which is what the first launch
after an update is.

## Agent detection

`AgentDetector` runs one script through the login shell that resolves each
known CLI with `whence -p` (zsh), `type -P` (bash) or `command -v`. The result
is cached by the host and sent on request; `agents(refresh: true)` runs it
again. Clients only offer agents with a path.

## Changes pane

The right side of the Mac window has two tabs, Git and History.

The diff of a file scrolls sideways as far as its longest line, with scroll
bars that stay visible: macOS hides them until you scroll, which would give
no hint that a line continues.

The two-panel view is laid out by `SplitDiff.rows` (in `AgentTermProtocol`)
from the same unified patch: lines both sides share are one row, a run of
removed lines followed by added ones is paired line by line, and what one
side has more of faces an empty row. Line numbers come from the hunk
headers. `SplitDiffView` (in `AgentTermTerminal`) draws it for both apps: one
vertical scroll view holding two horizontal ones, so the panels move down
together and sideways apart. Its rows are not lazy, since a lazy stack
inside the sideways scroll would have no height to be lazy in, so it shows
at most 2,500 rows and says when it left some out.

`GitDiff` shells out to `git`: `diff --cached` for what is staged, `diff` for
what is not, and `ls-files --others` plus `diff --no-index` for untracked
files, then splits the output per file. Renames are not detected
(`--no-renames`), so every entry is one path that can be staged on its own.
`GitActions` runs `git add`, `git restore --staged` (`git rm --cached`
before the first commit) and `git commit`, with `--literal-pathspecs` so a
file name is never read as a pattern.

The snapshot also says which branch the checked out one follows and how
far the two are apart (`git for-each-ref` with `%(upstream:short)` and
`%(upstream:track)`, one cheap call that asks nothing of the remote), and,
for a branch that follows none, the remote a first push would go to:
`origin`, else the first remote. `GitActions.push` runs `git push`, or
`git push --set-upstream <remote> <branch>` for that first push;
`GitActions.pull` runs `git pull --no-edit`, so it merges or rebases as the
repository is set up to. Commit, push and pull all run with
`GitActions.actionEnvironment`: `GIT_TERMINAL_PROMPT=0`, no askpass
program, `SSH_ASKPASS_REQUIRE=never` and `GIT_EDITOR=true`, so that neither
git nor a hook can sit waiting for a password: credential helpers and the
SSH agent still answer, and anything that would wait for typing fails with
git's own message, since there is no terminal to type in. A pull that
leaves a merge or a rebase under way is aborted, unless one was already
under way before it, which is the user's and is left alone.

Commit, push and pull run with the `PATH` of the user's login shell, not
the host's own: the host is started by the app or by launchd, whose `PATH`
is the system's short one, and git starts credential helpers (`!gh auth
git-credential`), hooks' tools and `git-lfs` by name. `LoginShellPath`
asks `$SHELL -l -i -c` for it once, prints it behind a marker so whatever
the startup files print is left out, and keeps it; when the shell says
nothing, the host's `PATH` is used. When git then says a program was not
found ("command not found", "is not a git command"), the shell is asked
again, and the action is run once more only if the `PATH` it gives is
another one: the program may have been installed since. The first ask
waits for the shell to start (at most 8 seconds), so the actions are never
run on the main thread. Under XCTest the user's own shell is never
started: `LoginShellPath` answers nothing there unless a test stands a
shell of its own in, so the tests read none of the user's startup files.
When a push or pull fails because nothing gave git
a sign-in ("could not read Username for '<url>'") and a credential helper
was not found, a sentence naming the host and the helper is put above
git's words: "git could not sign in to github.com: its credential helper
`gh` was not found."

## Commit messages written by an agent

`CommitWriter` builds the agent's input: the prompt, the list of staged
files with their counts (`git diff --cached --stat`), then each file's
diff, capped at 8,000 characters a file and 60,000 in all; files past that
are named without their diff. It then runs the agent once, without a
terminal, through the login shell as sessions are:

| Agent | Run as |
|---|---|
| Claude Code | `claude -p --no-session-persistence --strict-mcp-config --tools '' --model <m>`, the input on stdin |
| Codex | `codex exec --skip-git-repo-check --ephemeral --sandbox read-only -o <file> -`, the input on stdin |
| Antigravity | `agy --print "<input>"` |
| Copilot CLI | `copilot -p "<input>" --silent --no-custom-instructions --no-ask-user` |

The agent runs in `<state>/commit-writer`, not in the project: a headless
run inside the project would leave a conversation there, which the History
tab would list and `SessionSummaries` could pair with a session running in
that folder. Claude Code and Codex are told not to save one at all; what
Antigravity and Copilot save belongs to that folder of the host's, which
History leaves out. No agent is given a way to change anything: no tools
for Claude Code, a read-only sandbox for Codex, and for the other two no
approvals, which without a terminal means every tool request is refused.
The answer is taken out of a code fence or quotes if it came in one, and is
only ever put in the message field. A run can be stopped; it is also
stopped after three minutes.

The settings (agent, model, prompt) are the host's, in `settings.json`, so
the Mac's Write button and the iPhone's do the same. Both apps ask the host
with `writeCommitMessage`, the Mac too, though it runs git itself.

## How the Mac is doing

`SystemSampler` measures the Mac itself every three seconds while a client
is connected, and the host sends the result as `systemStats`:

| Figure | From |
|---|---|
| Processor | `host_statistics(HOST_CPU_LOAD_INFO)`: busy ticks over all ticks between two samples |
| Memory | `host_statistics64(HOST_VM_INFO64)`: app memory, wired and compressed, less what can be purged, as Activity Monitor counts it; `hw.memsize` |
| Network | `getifaddrs`: bytes in and out of every interface but the loopback, between two samples |
| Temperature | The hottest of the processor's sensors, through IOKit's HID event system; `ProcessInfo.thermalState` always |
| Battery | `IOPSCopyPowerSourcesInfo`: charge and whether it is charging |
| Uptime | `kern.boottime` |

The calls that read the temperature sensors are in IOKit but not in its
headers, so `SystemSampler` declares them itself. Where they find no
sensor, an Intel Mac for one, no temperature is sent and the apps show the
thermal state in words. Figures are rounded (a tenth of a gigabyte, a
kilobyte a second) so a Mac at rest is not announced again and again.
`SystemStatsView`, in `AgentTermTerminal`, draws them for both apps.

## SSH hosts

`SSHConfig.hosts` reads `~/.ssh/config`: the names after `Host`, following
`Include` (relative to `~/.ssh`, with `~` and wildcards) up to eight deep.
Patterns are skipped, and so is any name that is not plain (letters,
digits, `-`, `_`, `.`), because a name is put on a command line. Only the
names are sent to a client. `connectSSH` takes a name the host finds in
its own reading of the configuration, never a command.

## Keeping the Mac awake

`SleepGuard` holds an IOKit power assertion: `PreventUserIdleSystemSleep`,
or `PreventUserIdleDisplaySleep` when the display is to stay on. The host
holds it while the switch is on, a session exists (with "only while an
agent is working", a session whose agent is working: the host looks again
whenever a state changes), and, with "only on power",
`IOPSGetProvidingPowerSourceType` does not say battery; it looks
again on its timer, so plugging in or pulling the cable is followed within
seconds. A hold given a length carries the time it ends in the options;
when that passes the host switches it off and tells the clients. The
switch, the options and the end time are kept in `settings.json`. The Mac app calls it directly every few seconds while it is
in front. The iPhone asks the host: `diff` returns the list of files without
their diffs, which can be megabytes, and `diffFile` returns one file's diff.
The host keeps the last result per folder for 20 seconds so opening a file
right after the list does not run git again. Git and file reading for
clients run on a separate concurrent queue, off the queue that moves terminal
bytes.

## Files tab

`FileBrowser` (in `AgentTermHost`) lists a folder, reads a file and tells text
from images, other binaries and files too large to open, and creates,
renames, writes and trashes. Names are checked to be a single path
component, and an existing name is never overwritten. The Mac app calls it
directly; it is not in the protocol, so the iPhone has no Files tab.

`FilesModel` holds the tree (folders load when opened and are read again
every 5 seconds while the app is in front) and the open documents. Documents
belong to the window, not to the folder being browsed, so switching folders
does not close a file with unsaved edits. `active` names the document in
front; it is nil while a terminal shows. The tab strip lists sessions, then
documents, and the tab shortcuts count across both.

The editor is an `NSTextView` whose text storage is Highlightr's
`CodeAttributedString`, which recolors text as it is edited using
highlight.js. Markdown is rendered by MarkdownUI, with its code blocks
colored by the same highlighter. The editor and the previews live in the
`AgentTermEditor` target, which both apps use: on the iPhone the editor is a
`UITextView` on the same text storage.

The Mac reads and writes files itself. The iPhone asks the host: `files`
lists a folder, `readFile` returns text, or an image's bytes up to 8 MB,
`writeFile` saves, and `createFile`, `renameFile` and `trashFile` change the
tree and are answered with the folder's new listing. They run `FileBrowser`,
the same code the Mac app calls.

Mermaid diagrams are drawn by `MermaidView`, a `WKWebView`, since Mermaid is
a JavaScript library. `mermaid.min.js` (11.4.1, MIT) is checked in under
`Sources/AgentTermEditor/Resources` and shipped in the apps, so nothing is loaded
from the network: the page has a content security policy that allows no
remote source at all. The diagram's source goes into the page as escaped
text, and Mermaid runs with `securityLevel: 'strict'`.

Highlightr and `AgentTermEditor` each bring a resource bundle, which
`scripts/bundle-mac.sh` copies into the app's `Contents/Resources`.

## Channels

`AppChannel.current` is `.release` only when the code runs in a bundle whose
identifier is `com.manhpham.agentterm`; a development bundle, a bare
`swift run` and the test runner are `.dev`. The channel decides the app's
name, the folder the host keeps its files in, the default port and the scheme
of pairing links, which keeps a development build apart from an installed
release. See docs/RELEASE.md.

## Usage

`SessionInfo.usage` carries a `SessionUsage`: model, context tokens and
window, limits (window in minutes, percent used, reset time), premium
requests. The host fills it on the same six-second timer that names
sessions, so both apps get it with the session list.

`AgentUsage` reads the end of the conversation's file, the last 768 KB:
Claude Code's last reply with a `usage` object, Codex's last `token_count`
event (which carries `rate_limits`), Copilot's last `session.usage_record`,
Antigravity's last step with `input_tokens`.

Claude Code writes its rate limits nowhere, but hands them to its status
line command. So a session whose command is `claude` is started with
`--settings '{"statusLine":{"type":"command","command":"<agenttermd> statusline <file>"}}'`.
`StatusLineRelay` saves the JSON it is given to `<state>/usage/session-<id>.json`,
then runs the status line found in the project's or the user's settings
with the same input and prints what that prints. The host prefers this
report over the conversation file, since it has the limits and the size of
the context window. The file is removed when the session ends.

What an account has left is a second thing, `AccountUsage`, kept per agent
and sent to clients as `accountUsage` when it changes. `AccountUsageFetcher`
asks the agent's service, on the work queue, every five minutes while that
agent has a session, or a schedule waiting for its limit to start over
(that needs the time, also after the host started again):

| Agent | Sign-in read from | Asked |
|---|---|---|
| Claude Code | Keychain item `Claude Code-credentials`, else `~/.claude/.credentials.json` | `GET api.anthropic.com/api/oauth/usage?cedar_ember=1` (the query asks for banked limit resets) |
| Codex | `$CODEX_HOME/auth.json` | `GET chatgpt.com/backend-api/wham/usage`, and `wham/rate-limit-reset-credits` when resets are banked |
| Antigravity | Keychain item `gemini` / `antigravity` (go-keyring), else `~/.gemini/antigravity-cli/antigravity-oauth-token` | `POST cloudcode-pa.googleapis.com/v1internal:loadCodeAssist`, then `retrieveUserQuotaSummary` |
| Copilot CLI | `COPILOT_GITHUB_TOKEN`, `GH_TOKEN`, `GITHUB_TOKEN`, else `gh auth token` | `GET api.github.com/copilot_internal/user` |

Google answers by client name: the request says `antigravity/cli/<version of agy>`,
which is what returns every group of models.

The rules it keeps: HTTPS only, to those hosts only, redirects not followed;
a sign-in is never refreshed or written back, since renewing it is the
agent's business and doing it here could sign the agent out; an expired one
is not sent at all; nothing of it is logged, stored or put in a message to
a client. The outside world is passed in as `Environment`, so the tests run
against canned answers and never touch a keychain or the network.

## Conversation history

`AgentHistory` reads the files each agent CLI keeps about its own
conversations and lists those that ran in a folder. Conversations of
subfolders are left out by default, so that a workspace holding several
projects does not list every project's conversations as its own:

| Agent | Where it looks | Title | Resume command |
|---|---|---|---|
| Claude Code | `~/.claude/projects/<folder>/<session>.jsonl` | newest `ai-title` line, else the first prompt | `claude --resume <id>` |
| Codex | `~/.codex/sessions/**/rollout-*.jsonl` (first line has id and directory) | first prompt, from `~/.codex/history.jsonl` | `codex resume <id>` |
| Antigravity | `~/.gemini/antigravity-cli/cache/conversation_metadata.json` | its `Title` | `agy --conversation <id>` |
| Copilot CLI | `~/.copilot/session-state/<id>/workspace.yaml` | its `name`, else the first prompt | `copilot --resume=<id>` |

None of these are documented formats, so every reader treats missing or
unexpected data as "no conversations", and a CLI update can empty a section
until the reader is adjusted. Session files grow to many megabytes, so only
the first 256 KB and the last 64 KB are read. Session ids are put on a command
line that a shell runs, so ids with anything but letters, digits, `-`, `_` and
`.` are dropped.

The Mac app calls this directly, since it runs where the files are. The
iPhone asks the host with `history`, `resume` and `handoff`. For `resume` the
host builds the command itself from the agent and the id, after checking
both; for `handoff` it looks the conversation up again on its own disk, so a
client only ever names a conversation and never supplies a path or command.

## Session names

`SessionInfo` carries `agent`, `summary` and `conversationID`. The host fills
them in, so every client shows the same name without reading any files:

- `agent` comes from the command the session was started with.
- Every 6 seconds `SessionSummaries.assign` pairs agent sessions with the
  conversations `AgentHistory` finds in their folders. Agents do not say
  which conversation a terminal belongs to, so the pairing uses the agent,
  the folder and time: the oldest session takes the first conversation that
  began after it started. For Antigravity, which records no start, it is the
  conversation touched most recently since the session began.
- A resumed session's conversation is known from the start, and a pairing
  once made is kept, so a later, newer conversation does not steal it.
- Two sessions of one agent started in one folder within the same few
  seconds can be mixed up.

Handing off a running session uses `conversationID` when it is set.

## What the agent is doing

`SessionInfo.state` is an `AgentState`: `working(since:)`,
`waitingForPermission(AgentQuestion)`, `waitingForAnswer(AgentQuestion)`,
`done(said:)`, or nil when it is not known. `stateNote` says why it cannot
all be known, when there is something to say. The host works both out, so
every client shows the same.

**From the agent itself.** When the host starts an agent's session it gives
the agent hooks for that session only (`AgentHooks`), in the way each agent
takes them, without a change to the user's configuration:

| Agent | Given by | Events |
|---|---|---|
| Claude Code | `--settings`, with the status line | `UserPromptSubmit`, `PreToolUse`, `PermissionRequest`, `PostToolUse`, `Notification`, `Stop` |
| Codex | one `-c hooks.<Event>=...` for each | `UserPromptSubmit`, `PreToolUse`, `PermissionRequest`, `PostToolUse`, `Stop`, `Interrupt` |
| Copilot CLI | `--plugin-dir`, a plugin in the host's `hooks/copilot` | `userPromptSubmitted`, `preToolUse`, `permissionRequest`, `postToolUse`, `postToolUseFailure`, `agentStop` |
| Antigravity | `--add-dir`, the host's `hooks/antigravity` holding `.agents/hooks.json`, trusted for the session by `--settings` with the folders the user trusts | `PreInvocation`, `PreToolUse`, `PostToolUse`, `Stop` |

Every hook runs `agenttermd hook <agent> <event>`. It saves what it is told,
with the agent, the event and the time, in the file `AGENTTERM_EVENTS`
names: `events/session-<id>.json` in the usage folder, set in the session's
environment, which the agents pass on to their hooks. The command is the
same for every session because Codex trusts a hook by its command and asks
again when it changes. For Antigravity's `PreToolUse` the hook answers
`{"decision":"allow"}`, which leaves the decision to its own rules.

The host watches that `events` folder, which holds nothing else (Claude
Code's status line writes its usage next to it several times a second),
and reads a session's file when it changes, and on every refresh in case a change was missed; only the latest
event is kept, since the state follows from it. `AgentHooks.change` makes
the state from it, from what each agent was seen to tell its hooks on
2026-11-13 (Claude Code 2.1.323, Copilot CLI 1.0.110, Antigravity 1.5.7;
Codex 0.167.2 from its documentation, since it runs no hook it was not told
to trust). Working stays working since it began.

What cannot be known:

- **Codex** before 0.169 ran no hook until the user trusted it, and its
  session's state was not known until then. Codex 0.169 runs the hooks it
  is given for a session without asking, as trying it on 2026-11-14
  showed (#59), so its session carries no note about it any more: the
  note told the user to wait for a question that no longer comes.
- **Antigravity** says nothing when it waits for permission: its question
  comes after `PreToolUse`, with nothing in between. So while a tool runs,
  its state is not known, and `stateNote` says so.
- **The choices of a permission** are in no agent's hooks; those of a
  question are, for all but Codex, which has no question event.
- **A turn the user stops** is told by Codex (`Interrupt`) and not by the
  others. Escape alone or Control C typed to a working session makes its
  state not known until the agent says more.

## Worktrees

`GitWorktrees` (host): `create(in:agent:branch:from:)` runs `git worktree
add --no-track -b <branch> <top>/.agentterm/worktrees/<branch> <from or
HEAD>` after listing
`.agentterm/` in the exclude file, and returns the folder's place inside
the new worktree. Paths are written the way the folder is: git gives real
paths, and a folder opened through a symbolic link (`/var`, `/tmp`) would
otherwise not be found in them. `list(folder:inUse:)` reads `git worktree
list --porcelain`: each worktree's branch, commits ahead of the folder's
branch, files changed, and whether its folder is gone; a session counts
for the deepest worktree it is in. `finish` merges (`--no-edit`, left to
be resolved on a conflict as #42 has it, refused with uncommitted changes) and removes, pushes and runs
`gh pr create --fill` through the login shell, or removes with `--force`.

`GitDiff.snapshot` leaves out of the untracked files a folder whose `.git`
is a file pointing into the repository's own `worktrees` folder: a
worktree made inside the repository (#43), which `git status` lists as a
folder nobody tracks. Both apps ask for the list again when the changes on
show change in number, in branch or in what they are ahead by, so that a
chip's counts are not stale.

Messages: `createInWorktree(request:branch:from:)`, `listWorktrees(folder:)`,
`finishWorktree(folder:path:finish:deleteBranch:)` (refused while a session
runs in it), `setWorktreeSetup(folder:command:)`, kept in `worktrees.json`;
answered with `worktrees(folder:list:setup:)` and `worktreeFinished`;
`worktreeSetups` carries every folder's setup command to a client that
connects and whenever one changes (#34). What both apps say of a worktree
is in `WorktreeWords` and `WorktreeInfo.chipTitle/chipCounts/chipHelp`.
`SessionInfo.branch` names a session's worktree branch; `WorktreePath`
tells which folder a session in `.agentterm/worktrees` belongs to. The setup
command runs through the login shell in the new worktree before the
session, so the agent is still known by its command.

On the Mac, `AppModel.panelFolder` is the worktree shown (`shownWorktree`)
or the selected folder; the side panel's diff, commits, history and files
follow it, and selecting a session in a worktree shows that worktree.

## Schedules

`Schedule` (protocol): its agent, folder, prompt, `ScheduleTime` (`once`,
`daily`, `weekly`, `limitReset`), `SchedulePermissions` (`skipAll`,
`acceptEdits`, `ask`), whether it is on, whether a missed run catches up,
whether its warning was accepted, its last 20 runs and its next run. The
host keeps them in `schedules.json` next to `folders.json`, with until when
it looked (`checked`), from when each schedule is looked at (`from`, set
when it is made or its time changes), and the last limit reset each agent
ran for. Clients send `saveSchedule`, `removeSchedule` and are told
`schedules`.

**Shown.** `ScheduleOverview` (protocol), which both apps use, groups the
schedules with the sessions that still run: the runs whose session is one
of them (running), every schedule by its next run (then those with none,
then those off), and the other runs, newest first. Nothing is added to the
protocol: a run names its session, and the session list says which run.

**Saving.** Refused when the agent does not offer the mode, when it skips
permissions without its warning accepted, or without a prompt. Then
`ScheduleRunner.trustFolder` trusts the folder where the agent keeps that:
`projects[<folder>].hasTrustDialogAccepted` in `~/.claude.json`, and
`trustedFolders` in `~/.copilot/config.json` for Copilot CLI when it does
not skip permissions. The rest of those files is left as it was.

**Running.** Every 20 seconds, on its clock (`Configuration.now`, which
tests set), the host takes each schedule's first time after the later of
`checked` and its `from`: one that is now or past is due, once, however
many came between. A look more than 90 seconds after the last means the
Mac slept: a due time older than that is a missed run, run now or recorded
as missed as the schedule says. `limitReset` is due two minutes after the
latest `resetsAt` of the agent's account limits that it has not run for.
A due run of a schedule whose last run is still going (its session runs
and its agent is not done) is skipped; with two runs going, it waits. A
run whose agent's state is not known (its hooks never ran, as Codex's
before they are trusted, or it was interrupted) is going until it has
written nothing for an hour (`quietRunIsDone`), then counts as done. A run whose folder is not there is recorded as not
started: a session started there would be in the home folder. A
run is `ScheduleRunner.launch`: the agent's command with its switch
(`claude --permission-mode bypassPermissions|acceptEdits`, `codex
--dangerously-bypass-approvals-and-sandbox --dangerously-bypass-hook-trust`,
`copilot` with `COPILOT_ALLOW_ALL=true` or `--allow-tool=write`, `agy
--dangerously-skip-permissions` or `--mode accept-edits`) and the prompt,
started as a session with no client attached, `SessionInfo.schedule` and
`schedulePermissions` set; Antigravity gets the folder among those it
trusts for the session. A run's session that has counted as done for 24 hours is closed. The
hold on sleep is also taken while a schedule's next run is ten minutes or
less away.

## When an agent is done or needs you

Each app works out what to tell of from the states the host sends (#3),
with `AgentNotice.notices(in:told:)`: a session whose agent is done or waits
in a state it was not told in before. `told` is kept by the app for each
Mac across connections, so that coming back to the app tells nothing
twice; a session that works again, or whose state is not known, is
forgotten in it, so that what it says next is new.

**Whether someone is at the Mac.** The host works it out on its refresh and
when it changes: the Mac app says whether it is in front
(`appInFront(Bool)`, only to its own Mac's host), and `MacUse.idleSeconds`
reads macOS's `HIDIdleTime`. Five minutes without either is no one there.
A device that types or takes control of a session makes it no one there,
whatever the two say, until this Mac's own app types, takes control or
says `used` (a key or a click in its window, sent once after it was told
no one is there) (NOTE-7). Every client is told `macInUse(Bool)`; the
iPhone tells nothing while it is true.

**On the iPhone.** In front, a banner over the sessions list, for a session
other than the one on screen. Behind, a local notification
(`AgentNotifications`): the app asks iOS for a little more time when it
leaves the front (`beginBackgroundTask`), during which the connection
lives. A question's or a finished task's notification has a text reply
action that asks for the phone to be unlocked; the reply is sent as
`answer(session:to:text:)`, naming the state it answers, and the host types
it, then Return, only while the session is still in that state; else it
answers `error` and types nothing. A reply given while the connection was
gone waits for it. Notifications hide their text where iOS hides previews.
A question's choices are actions of its notification (#55): iOS takes a
notification's actions from its category, so a question with choices gets
a category of its own, named after the session, with an action for each of
the first nine choices (`AgentNotice.buttons`) and the text reply last, ten
being the most iOS shows. The body is the question alone
(`AgentNotice.words`). A choice is sent as a reply is, `answer` with the
choice's words as its text.

How the host types an answer is the agent's list's to say
(`AgentAnswer.steps`, #55). A prompt takes the text, then Return. A
question with choices is a list with its first choice marked, and Return
chooses what is marked: text and Return there answered every such question
with its first choice, in Claude Code, Copilot CLI and Antigravity alike,
as trying each showed. So an answer that is one of the choices is typed as
Down, once for each choice before it, then Return; any other answer goes
to the row after the choices ("Type something.", "Other", "Write-in..."):
Down past the choices, the text, Return, with a Return before the text in
Antigravity. The steps are typed 0.15 s apart, as a person types them. Only
the first of several questions asked together is told and answered.

**On the Mac.** A banner over the window for a session that is not the one
selected while the app is in front.

A banner is dropped when its session comes to the front (#60): on the Mac
when the session is selected with Sessions shown and the app in front of
the others (`selectedSession`, `show(_:)`, and when the app becomes
active: a session chosen in a window behind another app's is not before
the user's eyes yet), on the iPhone when its screen is put on the
navigation stack (`path`). The app then tells the host
`noticeSeen(session:state:)`, once for each state, when the agent is done
or waits. The host passes it on to every other client while the session's
state is still that one, and keeps it (`noticesSeen`) for a client that
connects later, which is told after its list of sessions. A client that is
told drops its banner of that session and state; the iPhone also takes
its notification of the session out of Notification Center
(`AgentNotifications.remove`), as it does when the session is opened on
the phone itself.

## The Live Activity

A widget extension, `AgentTermLiveActivity` (`iOS/AgentTermLiveActivity`),
with `AgentsActivityAttributes` (`iOS/Shared`, in both targets): the Mac's
name, and as content how many work and the names of those that wait and
are done. The app starts, updates and ends it (`PhoneModel.updateLiveActivity`)
whenever the sessions, the connection or `macInUse` change, as
`LiveActivityRule.decide` says: shown while connected, no one at the Mac
and an agent working or waiting; ended at once otherwise, but with the
last state left showing when every agent is done. Its link,
`<scheme>://session?id=<n>`, opens the session that waits. No push token is
asked for: updates come from the app while iOS lets it run.

Its bundle identifier is the app's with `.LiveActivity`; the release lane
signs it with a profile of its own from `match`.

## Shells an agent opens

AgentTerm's MCP server is `agenttermd mcp` (`AgentShellsMCP`): JSON-RPC, one
message to a line, on standard input and output. Its tools are
`open_shell`, `list_shells`, `read_screen`, `send_input`, `wait` and
`close_shell`. `wait` reads the screen every 0.2 seconds until a text
appears, or the screen has been the same for a while, or the time is up.

**Which session's agent it is.** The host gives every agent's session a key
of its own, with its port and its build, in `AGENTTERM_MCP` (`<port> <key>
<release or dev>`, then `use`); the agent passes its environment on to the
server it starts. The server signs in to the host as
any app on the Mac does, with the Mac's own token from the state folder,
and sends each request as `agentShell(id:key:request:)`. The host looks up
the session whose key it is and answers `agentShellResult(id:result:)` to
that connection only. A key names a running agent's session or nothing.
Without the variable, the server offers no tools. Nor does it in a session
of the other build: a released build and a development build each install
a server of their own (below), so an agent has both, and the one whose
build the variable does not name stays out rather than sign in to a host
with another host's token. A variable that names no build is from a host
of 0.6, and is the released build's. With "agents run their
commands in shells you see" on (the host's `agentsUseShells`, on by
default) the variable ends with `use`: the server's instructions are then
`AgentShellsInstructions.useShells`, and the agents are told the same
where each reads it (MCP-13): Claude Code is started with
`--append-system-prompt`; Antigravity gets a rule always on,
`.agents/rules/agentterm.md` in the folder it is given with `--add-dir`;
Copilot CLI gets `COPILOT_CUSTOM_INSTRUCTIONS_DIRS` naming a folder of the
host's with `instructions/agentterm.instructions.md` (after any the user's
environment names). Copilot CLI takes MCP servers' instructions only from
servers it allows, and Antigravity not at all. Codex follows the server's.

**What it may reach.** A shell it opens is a session like any other, in the
agent's folder and at its size, with `SessionInfo.openedBy` naming the
agent's session. Only that agent types into it and closes it; every agent
lists and reads the shells any agent opened, and `agentShellResult`'s
`shells(_:own:)` says which are the asking agent's (#61). So what runs in
an agent's shell is what that agent started, and no agent has to guess
from a screen whether a shell is free: one that has none, or whose own is
busy, opens another. Typing into or closing another agent's shell is
refused with words that say to open one; so it is for a shell whose
agent's session has ended, which is nobody's: it stays open for the user,
and nothing takes it over. A session that is resumed or handed off is, to
the host, another agent, and only reads the shells it opened before. An
agent never reaches the user's sessions or an agent's session. A command
whose first word is an agent's is refused. Typing is the same as typing:
text, and keys by name turned into the bytes a terminal sends
(`TerminalKeys`). When the agent's session ends, the server it started
ends with it. The apps name a shell's agent on its row
(`SessionInfo.openedByName`).

**When it cannot reach its host.** The server's line to the host
(`AgentShellsLink` in `agenttermd`) signs in when the server starts. A
connection that is refused or closed answers whoever waits at once, with
the reason in words: the host is not running on its port, the host
refused the sign-in (it answers a wrong token with `error("invalid
token")` and closes), or the connection was lost. Each later call tries
the host once more, so it fails as fast while the host is gone and works
again once it is back; only a host that is up and silent is waited for,
fifteen seconds. The host notes a sign-in it refused from a client on this
Mac named `MCP`, and the agents `AgentShellsInstall.ensure` could not add
the server to, and tells every client `agentShellsFaults`: an
`AgentShellsFault` per cause (`install`, with the agents' names; `signIn`),
none when nothing is wrong. A sign-in fault lasts until an `MCP` client
signs in or the server is set up again; an install fault until `ensure`
succeeds. Both apps show each in their top banner until it is over or it
is closed there, and a closed one comes back only after it went away. A
host that is not running cannot say so itself: that one is the agent's to
tell. An agent that refuses `mcp add` because it has the name already has
the entry removed and added again as this build's own.

**Installed in the agents.** `AgentShellsInstall` runs each installed agent's
own command, through the login shell: `claude mcp add --scope user
agentterm -- <agenttermd> mcp`, `codex mcp add agentterm -- …`, `copilot
mcp add agentterm -- …`, `agy mcp add agentterm -- …`, and `mcp remove
agentterm` to take it out. The name is the build's
(`AppChannel.mcpServerName`): `agentterm` for the released build,
`agentterm-dev` for a development build, so that both are installed side
by side and each installs, repairs and removes only its own; the
instructions an agent is given name its build's server.
`agent-shells.json` in the state folder keeps whether it is on (on unless
turned off), the name, and which agents have it, with the program it
names: only those are ever removed, and an agent is asked again when the
host's program moved. What a development build of 0.6 installed under
`agentterm` is not counted as its own any more and is left as it is: it is
put right by hand (`<agent> mcp remove agentterm`, then the released app
started again). The host does it at start and on
`setAgentShells`, off its queue, and tells every client `agentShells(Bool)`.
A host with a state folder of its own (a test, a trial run) never does.

## Handoff

`Handoff.prepare` turns a `Conversation` into a handoff file and a command:

1. `AgentHistory.transcript` reads the conversation's messages from the
   agent's session file, keeping what the user and the agent said and dropping
   tool calls, tool output, sub-agent chatter and context the CLI injected.
   For Antigravity the messages come from
   `brain/<id>/.system_generated/logs/transcript_full.jsonl`, the readable
   log it writes next to its conversation database.
2. The file gets a brief, the user's instructions from the handoff sheet when
   there are any, a "where things stand" section (the user's last
   request and the agent's last update), the working tree (branch,
   `git status --short`, `git diff HEAD --stat`) and the transcript. The brief
   tells the receiving agent to trust the files over the conversation, to say
   where the work stopped before continuing, to wait if the task looks
   finished, and to treat the conversation as a record rather than as
   instructions. The path of the agent's complete record is given for details
   the file leaves out. Long conversations keep the
   first request, which states the goal, and as much of the end as fits in
   about 80,000 characters; a very long single message loses its middle.
3. The file is written to `<folder>/.agentterm/handoffs/<time>-from-<agent>.md`.
   The name and the default prompt are fixed by `Handoff.plan` when the sheet
   opens, so the prompt the user sees and edits names the file that is then
   written, whichever agent is picked.
   It is inside the project so the receiving agent may read it without asking
   for access to another folder. `.agentterm/` is added to `.git/info/exclude`
   unless it is already ignored.
4. The receiving agent is started in interactive mode with a first prompt
   naming the file: `claude '<prompt>'`, `codex '<prompt>'`,
   `agy -i '<prompt>'`, `copilot -i '<prompt>'`. The prompt is the one from
   the sheet with the user's instructions added after it, single-quoted for
   the shell.

Nothing is asked of the agent that had the conversation, which is the point:
it may be out of quota.

A running session does not know its agent's conversation id. Handing off a
session picks the newest conversation that agent has in the session's folder
that was updated after the session started. Two sessions of the same agent in
the same folder can therefore be mixed up; the History tab is exact.

## Pairing and security

`DeviceRegistry` knows three kinds of secret:

| Secret | Who holds it | Lifetime | Good for |
|---|---|---|---|
| Local token | The Mac (`token`, mode 0600) | Permanent | Everything, but only on connections that arrive on the loopback interface |
| Pairing code | Shown as QR code or link | One use, five minutes, and until the pairing screen closes | Getting a device token |
| Device token | One paired device (Keychain) | Until the Mac removes the device | Sessions, folders, agents. Not pairing or removing devices |

- A device that is not paired sends `pair(code, device)` as its first message.
  The host answers `paired(device, token)` once and then treats the connection
  as that device. Afterwards the device connects with `hello(token)`.
- The host stores only the SHA-256 of device tokens (`devices.json`), so that
  file cannot be used to connect.
- The local token is refused on the Tailscale listener. If it leaks it is
  useless to anyone who is not already on the Mac.
- `createPairingCode`, `cancelPairingCode`, `listDevices` and `revokeDevice`
  are accepted only from a connection that authenticated with the local
  token. Revoking closes the device's live connections.
- The pairing link is
  `agentterm://pair?host=<tailscale name>&port=<port>&code=<code>&name=<mac>`.
- `agenttermd pairing-link` asks the running daemon for a code and prints the
  link. The iOS Simulator has no camera, so `scripts/pair-ios.sh` uses it.
- `Tailscale.status()` decides what the pairing screen shows. Tailscale counts
  as installed when its app or command line tool is found; as ready when the
  Mac has an address in Tailscale's range and the CLI, if it answers, reports
  the backend as running. An address alone is enough where the CLI is missing.
  The screen re-checks every 3 seconds while it is open.
- The host listens on `127.0.0.1` and on the Mac's Tailscale address
  (100.64.0.0/10), found with `getifaddrs`. It checks every 15 seconds so it
  follows Tailscale going up, down or changing address. It never listens on
  other interfaces.
- The WebSocket itself is not encrypted. Loopback traffic stays on the Mac and
  Tailscale traffic is encrypted by WireGuard.
- A token is still required on Tailscale, because other devices and shared
  nodes in a tailnet can reach the port, and the port is shell access.
- Token and code comparison is constant time. Unauthenticated connections are
  closed after 10 seconds.

## Vietnamese input

- **Host**: bytes pass through untouched and the locale is UTF-8. Covered by
  tests at the PTY level and end to end.
- **macOS**: SwiftTerm's view implements `NSTextInputClient`, so input methods
  that use marked text compose at the cursor. Tools that retype with
  backspaces send DEL bytes followed by the new text, which the shell and the
  agents handle themselves. Both paths are checked by hand, against the
  matrix in the spec.
- **iPhone**: prose goes through a native compose field and is sent as
  complete text, so the emulator never sees a composition. The key bar sends
  control keys directly. The text and the Return that submits it are sent 80 ms
  apart, because agents treat a burst ending in Return as a paste and do not
  submit it. Multi-line text is wrapped in bracketed paste.

## macOS app structure

- `AppModel` holds all state: connection, folders, sessions, agents, the diff
  and one `TerminalController` per session.
- `TerminalController` wraps a SwiftTerm `TerminalView` and is its delegate.
  Terminal views are kept alive while their session runs, so switching
  sessions keeps scrollback.
- If the app cannot connect, it starts the `agenttermd` that sits next to its
  own executable, in a new session so it outlives the app, and retries.

## A part that stopped

A part of AgentTerm that stops without being asked to is reported to every
client in a message of its own, `failures([PartFailure])`, rather than left
for the clients to work out from a list that emptied. The parts are the
host, a session's program, the hold that keeps the Mac awake, and the
status line relay (see "The other parts" below). A `PartFailure` says:

| Field | Means |
|---|---|
| `id` | Names the report, for `dismissFailure` |
| `part` | Which part: `host`, `session`, `keepAwake`, `statusLine`. Text, not a closed list, so a client reads a part added after it was built |
| `name` | Which one, for a part there are several of (a session); nil for the host |
| `at` | When it stopped, as near as is known |
| `ended` | The sessions that ended with it: name, folder, agent |
| `restarted` | Whether it was started again by itself |
| `broken` | It stopped too often (three times in sixty seconds) and is not started again by itself |
| `reason` | Why it stopped, or why starting it again failed, when that is known |

The host sends the list of reports nobody has seen on connecting and
whenever it changes. A client that dismisses one (`dismissFailure`) drops
it for all of them. The list is kept in `failures.json` in the state
folder, at most twenty, so a host that is restarted, or dies itself, still
has it. Both apps word a report the same way (`PartFailure.headline`,
`details`).

**The other parts.** None of them is started again by the host:

- **A session's program** that dies of SIGKILL or of a signal a crash
  gives (SIGSEGV, SIGBUS, SIGILL, SIGABRT, SIGTRAP, SIGFPE) is reported
  with its session, which ends as it always did. A program the user
  stopped (Control C, SIGINT) or that ended by itself is not, nor one whose
  end was asked for: closing a session sends SIGHUP and, three seconds
  later, SIGKILL, and the host notes that the end was asked for before it
  sends either. A program that exits by itself with the status a signal
  would give (137 for SIGKILL) is taken for killed. Offering to resume the
  agent's conversation in a new session is for a later release.
- **The hold that keeps the Mac awake** that macOS refuses is reported
  once. The host asks for it again on every refresh, and the report says
  so once it is held (`restarted`).
- **The status line relay** runs once each time Claude Code updates its
  status line, so there is nothing that keeps running to start again.
  When it cannot save what it was given, it writes why next to the file
  (`<file>.failed`) and removes that once it saves again. The host looks
  for it on every refresh and reports it once for the session, and again
  only if it was saved in between.

**How a death is told from a stop.** A running host keeps a marker,
`host-<port>.json` in its state folder (`HostMarker`): its process, and its
sessions by name, written again when they change. It touches the file
every few seconds, so its modification time is when the host was last
known to be alive. A stop that was asked for (SIGTERM, SIGINT: Restart
Host, replacing another copy's host, logging out) removes the marker before
the clients' connections close. A host that is killed or crashes cannot.
So a host that starts, once its port is its own, and finds a marker whose
process no longer runs as a host knows the one before it died: it adds a
report of the host, with that marker's sessions and time, and writes its
own marker.

**The host watched by the Mac app.** When the app's connection to its own
host closes, the app looks for the marker: there, the host died; gone, it
was stopped. A death is counted. The app starts the host again by itself
(`DaemonLauncher.startHost`: through launchd while Start at Login is on,
see below), and the new host reports what ended. After
three deaths within sixty seconds the app does not start it again: the
launch screen says that the host keeps stopping, how often, and how the
last one ended, with Try Again, which starts over. The app knows how a
host it started ended because it is that host's parent: it waits for it
(`DaemonLauncher.watch`), which also keeps ended hosts off the system's
books, and puts the status in words (`describe(exitStatus:)`: killed,
crashed, or exited, with the last "agenttermd: …" line of its log). A host
it started that ends before it ever answered could not be started, and the
app says so at once with that reason, instead of trying twenty times. A
host started by someone else, launchd or a test, gives the app no status:
the report then says only that it stopped.

Until 0.6.0 the app started its host again only the first time it was
lost: the flag that says it has started one was never reset after a host
answered.

**How the host is started: one owner.** With Start at Login on, the host
is a launch agent (`LoginItem`): `~/Library/LaunchAgents/<bundle
id>.host.plist`, with `RunAtLoad`, and `KeepAlive` = `SuccessfulExit:
false`. launchd starts it at login and starts it again when it crashed or
was killed; a host that was stopped as asked (SIGTERM, SIGINT) exits with
status 0, and launchd leaves it. While the switch is on, the app does not
spawn the host either: it asks launchd (`DaemonLauncher.startHost`), so
there is never a second host racing the first for the port.

`startHost` decides, in this order:

1. launchd runs the job already (it started it again after a death):
   nothing to start.
2. The switch is on: the property list is brought up to date
   (`refresh()`: the host of this app, as this version writes it), the job
   is unloaded if launchd still has it, and loaded (`launchctl bootstrap`),
   which starts it at once. A job launchd is waiting to start again is
   started this way too, instead of after launchd's ten-second throttle.
   Should launchd refuse it, the app spawns the host itself.
3. The switch is off: a job launchd still has loaded from before is
   unloaded, so it cannot start a host next to the app's, and the app
   spawns its own (`DaemonLauncher.launch`).

The switch only writes or removes the file. Turning it on loads nothing,
since that would start a second host: the host that runs then is the
app's until it next stops, and launchd's from the next start on. Turning
it off unloads nothing, since that would stop the host: launchd keeps
watching the host it runs until it stops.

A host launchd started is not the app's child, so the app asks launchd
how it ended (`jobState()`: `launchctl list <label>`, whose
`LastExitStatus` is the status `waitpid` gives) and puts it in the same
words. One that ended before it ever answered could not be started: the
app says so, and unloads the job until Try Again, since launchd would
only start it again every ten seconds.

**Broken under launchd.** With the app closed nobody counts deaths but
the host. The marker carries the times of the deaths within the last
minute from one host to the next (`HostMarker.deaths`). A host that
starts and finds that its predecessor was the third to die within sixty
seconds reports that death as broken (`broken`, not `restarted`), removes
the marker, and exits with status 0 (`StartError.keepsDying`), so that
launchd does not start it again. The next start is one the user makes:
logging in, opening the app, Try Again. With the app open the app counts
as before, says the host keeps stopping after the third death, and
unloads the job. Try Again clears the deaths in the marker
(`forgetDeaths`), keeping the marker itself so the death it holds is
still reported.

## Another Mac

The Mac app can show another Mac instead of the one it runs on
(`AppModel.remote`), the way the iPhone shows a Mac. The menu in the
toolbar, before the agents, switches between this Mac and the paired ones.

- Pairing is by link: a Mac has no camera pointed at the other's screen, so
  the link under the pairing code is pasted (`pairMac(link:)`). The code is
  traded for a token of this Mac's own, as a phone's is. The paired Macs
  are in the Keychain (`RemoteMacStore`); a host with a state folder of
  its own keeps them in that folder, which leaves the Keychain to the
  real app.
- The terminals already went through the protocol. Changes, history,
  handoff and files did not: on its own Mac the app reads them from disk,
  which is faster and needs no host. For another Mac the same functions of
  `AppModel` and `FilesModel` send the messages the iPhone sends (`diff`,
  `diffFile`, `gitStage` …, `history`, `handoffPlan`, `handoff`, `files`,
  `readFile` …) and take the answers in `handle`. A list of changes from
  another Mac comes without the diffs, so the diff on show is asked for
  by itself after each list.
- What only this Mac's disk can do is not offered: Show in Finder, an
  open panel (a sheet lists the other Mac's folders instead), dropping
  folders from the Finder, pairing a phone, restarting the host. The app
  never starts a host for another Mac; one that cannot be reached is
  said so, with a way back to this Mac.
- Switching Macs drops what was on screen and connects again. It is
  refused while a file has unsaved changes: they are on the Mac that
  would be left.

## iPhone app structure

- `PhoneModel` holds the paired Macs, the connection and the single
  `TerminalController` for the session on screen.
- There is one connection at a time, to the Mac on screen. Switching Macs
  closes it and opens another, so a Mac that is not on screen costs nothing
  and its sessions are not resized by this phone.
- The paired Macs, each with this phone's token for it, are kept in the
  Keychain as one list. Pairing again with a Mac replaces its entry.
- `PairView` scans with VisionKit's `DataScannerViewController`. Where there
  is no camera (the simulator) the link can be entered as text, and the app
  also opens `agentterm://pair` links.
- `TerminalScreen` stacks the terminal, the key bar and the compose field.
  What is written in the compose field and not sent is kept per session on
  the phone (`PhoneModel.composeDraft`), so it is there again after leaving
  the terminal or closing the app. The Mac needs nothing for this: what is
  typed there is already in the program's own input, in the session.
  The keyboard shrinks the terminal's frame, which resizes the PTY.
  While the keyboard is up, a button at the end of the key bar puts it
  away (`KeyboardWatcher`); the other screens with something to write in
  have that button in a bar above the keyboard.
- With the phone on its side (`verticalSizeClass == .compact`) the
  terminal screen has no navigation bar: back, the keys, the compose field
  and the session's menu share one row under the terminal. Stacked as they
  are upright they would leave the terminal a single line once the
  keyboard is up.
- Wherever a screen waits for the Mac it shows `LoadingView`, on the Mac
  app too: nothing for the first 300 ms, then a spinner and what is being
  waited for, and after ten seconds that it is taking long, with Try Again
  where asking again is possible. A terminal is covered by it while the
  session's earlier output is on its way (`replaying`).
- While the app is in front it reconnects after a drop, at once the first
  time and then every few seconds, and re-attaches to the session that was
  open. The terminal screen says so meanwhile.
- A drop is rarely announced: the network changes or the app was asleep,
  and what is sent just goes nowhere. `AgentTermConnection` therefore asks
  a host that has been quiet for four seconds for a WebSocket pong, and
  closes a connection that does not answer within six, which is what lets
  the app connect again. Coming back to the front asks at once. Bytes that
  keep arriving count as an answer: a large message over a slow link, a
  replay or a file, holds the pong back behind it, and that link is slow,
  not gone.

## Testing

- `swift test` covers the protocol, PTY behavior, the size arbiter, parsing
  and the host server end to end over a real loopback WebSocket.
- `scripts/test-ios.sh` runs an XCUITest in the simulator against two
  throwaway hosts: pair by link, start a shell, send Vietnamese text from the
  compose field, use the key bar, go back, pair the second host, and switch
  between the two. `LANDSCAPE=only` runs the part that turns the phone on

## Known limitations

- The iPhone app has not been run on a real device.
- Session rows on the iPhone are named after the session's working directory
  when it is not a listed folder; the home directory shows as the user name.

- The lines above the screen that a client is sent are the 10,000 newest.
  Images a program drew are not among them.
- SwiftTerm resets some terminal modes when its grid is resized from code,
  which happens when another device takes over the size.
- A terminal wider than the Mac window (a phone in landscape next to a narrow
  window) is clipped rather than scaled.
- The host does not apply backpressure to a slow client.
- The daemon is started by the app, or by launchd when the user asked for
  Start at Login. With Start at Login off and the app closed nothing
  watches it: a host that dies then is reported only when the next one
  starts. With it on, a host the app started before the switch was turned
  on is launchd's only from its next start.
- A host that cannot even start (its port taken at login) is started
  again by launchd every ten seconds while the app is closed: it is not
  counted as dying, since it never ran.
